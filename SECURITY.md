# Política de segurança

*English version below.*

## Versões com suporte

Só a versão mais recente, a última release publicada, recebe correções de segurança. Atualize para ela antes de relatar.

| Versão | Suporte |
|---|---|
| Última release | sim |
| Qualquer versão anterior | não |

A v0.5.1 precisa do Claude Code 2.1.251 ou mais novo. Em CLI anterior à 2.1.251 o plugin não funciona: nenhum hook carrega e, sem o registro do SessionStart, a barra também fica vazia. No spike S11 da parte 2, a 2.1.250 recusou os eventos `PreModelSwitch` e `PostModelSwitch` do `hooks.json` e registrou zero hooks do plugin. Ficam de fora a guarda (P1 a P5), a linha de consumo do início de sessão, os avisos e a barra. A mínima é 2.1.251; a 2.1.250 falhou, e a 2.1.251 não foi testada isoladamente.

## Como relatar uma vulnerabilidade

Use o relato privado de vulnerabilidades do GitHub: aba **Security** deste repositório → **Report a vulnerability**. Nunca relate uma vulnerabilidade por issue, pull request ou discussão pública.

Ajuda incluir a versão do plugin, o sistema operacional, a versão do Node, os passos para reproduzir e o impacto. Use só dados sintéticos: não anexe transcripts reais, caminhos pessoais, credenciais nem tokens de acesso.

## Prazo de resposta

Confirmamos o recebimento em até 7 dias.

## Escopo

O código do plugin neste repositório: `src/`, `hooks/`, `skills/`, `.claude-plugin/`, `bench/`, `.github/`, `kit/` (hadouken-kit) e `rea/` (hadouken-rea). O Claude Code, o `gh`, o Node.js e o GitHub têm canais próprios e ficam fora deste escopo.

A garantia do plugin (spec, seção 8.1): nenhum dado lido por ele vira código executado, comando de shell, caminho de API arbitrário, sequência de terminal ou instrução com a autoridade do plugin no contexto do Claude. Isso vale para os arquivos em `~/.claude/hadouken/`, os transcripts, o JSON da statusline, o stdin dos hooks, as respostas do GitHub e os argumentos de skill.

Resumo do modelo de ameaças:

- **S1, arquivo de dados adulterado** (`estado.json`, `alertas.json`, `projecao.json`, `config.json`, `historico.jsonl`, índices) para injetar texto no contexto do Claude pelos hooks. O texto injetado é montado só com números finitos validados e rótulos de listas fixas do código. Arquivo fora do schema vira "sem leitura". Desde a v0.2.0 (spec §12.7): o histórico de leituras do `estado.json` é validado ponto a ponto (no máximo 90 pontos, `at` entre 3 horas atrás e 5 minutos à frente, porcentagens de 0 a 100; o resto é descartado, e um histórico que não é lista vira lista vazia); a previsão só sai com pelo menos 3 pontos em 6 minutos, inclinação positiva e finita e instante antes do reset; o número de sessões ativas só conta ids válidos, nunca passa de 50 e só aparece como inteiro; a memória de projeção fica num arquivo só dela, o `projecao.json`, que guarda no máximo 256 sessões, só aceita ids válidos e faixas da lista fixa, é gravado de forma atômica e só quando muda, e nunca é criado vazio; conteúdo hostil nele (arquivo acima de 1 MB, chaves como `__proto__` ou `constructor`, tipos errados, faixa fora da lista, instante de reset que não é número finito entre 0 e 10¹¹ s, texto com instrução) faz o arquivo valer como vazio (o lado seguro: a faixa atual é anunciada de novo) até ser regravado limpo; e o aviso de projeção leva só números validados e texto fixo.
- **S2, texto malicioso** em transcripts, nomes de projeto, ids de sessão, modelo, effort, repos ou campos do GitHub mostrados no `/consumo`. Um saneamento único (`sanear`) remove caracteres de controle, sequências ANSI/OSC, `|`, crases e quebras de linha, e limita o texto a 64 caracteres. O effort só é aceito de uma lista fixa, e o relatório declara que esses campos são dado, não instrução. O nome curto do modelo (`Opus 5.5`, v0.2.0) só sai de um nome saneado que casa um padrão fixo, ancorado nas duas pontas; é só exibição e não muda somas, chaves nem o `--json`. A seção "Sessões abertas (última hora)" (v0.2.0) usa a mesma limpeza das outras tabelas, e o markdown revalida item a item a lista `sessoesAbertas` do JSON antes de mostrá-la.
- **S3, sequências de terminal** (ANSI/OSC, como links ou títulos falsos) chegando à barra por `model.display_name` ou outro campo. Todo texto externo passa por `sanear` antes de ser impresso; as únicas sequências ANSI da barra são as cores fixas do código. Os nomes externos perdem também os glifos que a barra desenha (`│`, `·`, `↻` e, desde a v0.2.0, `▰`, `▱`, `┃` e `→`), para nenhum nome forjar um separador, uma barrinha, a marca do ritmo ou uma previsão; o painel de limites do relatório só tem números validados e rótulos do código.
- **S4, injeção de shell pelos argumentos de `/hadouken:consumo`.** A skill nunca repassa `$ARGUMENTS`: roda um de dois comandos fixos, com ou sem `--json`, e a CLI ignora qualquer outro argumento.
- **S5, repo malicioso em `config.json`** (por exemplo `../../user` ou argumentos extras). Só é aceito `dono/repo` que case `^[A-Za-z0-9-]{1,39}/[A-Za-z0-9._-]{1,100}$`, sem `..`. O `gh` é chamado por `execFile`, nunca por um shell.
- **S6, shim adulterado** em `~/.claude/hadouken/bin/` para executar outro código. O hook SessionStart reescreve os shims a cada sessão a partir do conteúdo esperado, e os shims não leem nada de fora.
- **S7, instalador acionado por outra skill ou pelo modelo** sem o usuário saber. `/hadouken:instalar` tem `disable-model-invocation: true`, pede confirmação explícita antes de gravar e grava só a chave `statusLine`, com backup.
- **S8, cadeia de suprimentos.** Zero dependências; CI com `permissions: contents: read`, actions fixadas por SHA de commit e Dependabot semanal.
- **S9, arquivo gigante ou malformado** para travar um hook ou a barra. A leitura tem limites de tamanho (arquivos de estado até 1 MB; linha de transcript acima de 5 MB é ignorada), os hooks têm prazo e sempre terminam com código 0.
- **S10, o modelo carrega `/hadouken:liberar`** pela ferramenta Skill. A skill tem `disable-model-invocation: true` e um corpo inerte, que só diz que nada foi liberado. Toda liberação acontece no hook UserPromptExpansion, nunca no corpo. O modelo também não libera por uma tarefa agendada (`CronCreate`), pela volta de um `/loop` (`ScheduleWakeup`) nem por uma rotina (`RemoteTrigger`): o hook da agenda nega no PreToolUse, sempre, a chamada com o pedido de liberação em qualquer campo de texto; a documentação diz que `disable-model-invocation` impede o disparo agendado de rodar a skill; e o hook do liberar só aceita a expansão do comando digitado (lista fechada: `command_source` `plugin` e `expansion_type` `slash_command`), recusando e registrando qualquer outra origem. Na sessão manual do roteiro (Claude Code 2.1.285 a 2.1.287), o CronCreate e o ScheduleWakeup com `/hadouken:liberar 2h` foram negados no PreToolUse, com o evento `liberacao-recusada` e o nome da ferramenta, e o `/loop 1m /hadouken:liberar 2h` foi negado já no agendamento (CronCreate): nada foi agendado nem disparado, e não houve `liberacao.json`. Pelo spike S6 da parte 2, um disparo de cron ou de `/loop` chega ao UserPromptSubmit como um prompt digitado, sem marcador (veja S22 e S23). A tarefa durável gravada direto no `.claude/scheduled_tasks.json` não foi exercitada, porque o agendamento foi recusado antes; ela continua no R1. Desde o aprendizado local (v0.4.0), o hook da agenda nega do mesmo jeito a chamada com `/hadouken:aprender` (`hadouken:aprender`, ou `/aprender` como palavra), porque o `aprovar` afrouxa a guarda e o `desligar` tira o aprendizado; o texto da negação cita os dois comandos, e o hook do aprender usa a mesma lista fechada de origem (L5).
- **S11, o modelo abre uma sessão `claude -p` para se liberar.** O hook recusa a liberação quando `CLAUDE_CODE_ENTRYPOINT` indica `-p` ou SDK, e a P4 nega `claude ...` por Bash e PowerShell com a guarda disparada. O sinal do entrypoint pode ser falsificado; é limite declarado (R1).
- **S12, S18 e S19** não se aplicam: a liberação não usa código (decisão D4, opção C, de 2026-09-29).
- **S13, forjar `liberacao.json` ou apagar `guarda.json` pelas ferramentas de edição.** A P5 nega Write, Edit, MultiEdit e NotebookEdit na pasta de dados, sempre. Também nega, sempre, nos `settings.json` e `settings.local.json` do usuário e no próprio plugin; nos settings de projeto, nega a edição que mexe nos hooks ou nos plugins (R1). O caminho é resolvido pelo caminho real, com `..`, maiúsculas no Windows e links. O filtro `if` do Claude Code não casa o nome curto 8.3 nem um `HADOUKEN_HOME` fora de `~/.claude/hadouken` (R1). Nos settings de projeto, o `if` é ancorado com `//**/` desde o commit 1e69086: no spike S13 da parte 2, o `**/` sem âncora não casava caminho absoluto no Windows, e com a âncora a edição foi negada ponta a ponta (`P5:settings-projeto`). Duas regras `if` casam o `settings.json` do usuário, então cada edição dele grava dois eventos `arquivo-negado`; a negação é a mesma, só a contagem dobra.
- **S14, forjar pelo shell** (R1). Um processo do mesmo usuário escreve onde o usuário escreve. Mitigações: P4, a proibição no texto do bloqueio, a barra mostrando toda liberação (com "liberação sem origem" quando falta o evento) e "guarda desligada", e o registro de eventos. Desde a v0.4.0, a P5 de config (hook `ConfigChange`, R1) segura, na sessão em curso, a mudança de `disableAllHooks`, `enabledPlugins` ou `hooks` nos settings feita pelo shell.
- **S15, afrouxar o `config.json`.** A trava não cai por mudança de configuração; só a liberação a solta.
- **S16, JSON hostil ou gigante nos arquivos novos** (`guarda.json`, `liberacao.json`, `modelos.json`, `limites-atingidos.json`, `despachos-fable.json`, `guarda-eventos.json`). Leitura com `lstat` (link simbólico é inválido), teto de bytes e reconstrução só dos campos conhecidos. `guarda.json` ilegível conta como guarda disparada; `liberacao.json` ilegível conta como nenhuma liberação.
- **S17, texto hostil chegando ao Claude pelas mensagens da guarda** (nome de modelo, nome de agente, texto do limite, argumento da liberação). Todas as mensagens são modelos fixos, preenchidos com números e rótulos do código. O texto do StopFailure só é classificado, e o argumento da liberação só passa por uma gramática fechada.
- **S20, hook que estoura o tempo** deixa o despacho passar (R2). Caminho curto medido no bench; timeout de 10 s nos hooks de bloqueio.
- **S21, corrida entre sessões gravando a trava.** União das travas e renomeação atômica; uma gravação perdida volta na avaliação seguinte.
- **S22 e S23, a guarda travando a si mesma ou perdendo trabalho em andamento.** A P2 deixa passar `/hadouken:...` e o turno automático `<task-notification>`, que entrega o resultado de um subagente em segundo plano. Pelo spike S6 da parte 2, os disparos de cron e de `/loop` chegam ao UserPromptSubmit com as mesmas chaves de um prompt digitado, sem marcador. A P2 os trata como prompt comum: numa sessão Fable com a guarda disparada, o disparo é bloqueado (decisão 15 do plano da parte 2); fora do Fable, passa. A P1 e a P3 continuam valendo no turno disparado. O R3 não muda.
- **S24, privacidade.** Os módulos da guarda não importam rede nem `child_process` (conferido por teste), e os arquivos novos guardam só números, horários, ids validados e rótulos.
- **S25, créditos de uso depois do limite do Fable.** O G6 só sai com o escopo `fable` da liberação, que avisa que o Fable pode consumir créditos.
- **S26, o painel executa `claude`** (v0.3.0). Para ler o `/usage`, o painel roda `claude -p /usage` em modo enxuto, sem plugins, MCP, hooks nem persistência de sessão. O executável é procurado só em `~/.local/bin/` e nos diretórios do `PATH` (no Windows, só `claude.exe`, nunca `.cmd` ou `.bat`) e chamado por `execFile`, sem shell. Os argumentos são fixos, a saída tem teto de 64 KiB e o tempo, de 30 s. No prazo, o plugin mata a árvore inteira do processo (no Windows, `taskkill /t /f` do System32), e a leitura seguinte espera 15 min, como depois de qualquer falha (formato inesperado, erro). Da saída só saem números, por regex ancorada. Se o resultado indicar custo (`num_turns` ou `total_cost_usd` diferente de zero, ou ausente), a leitura para por 24 h. Com zero turnos e custo zero, uma resposta que não venha do comando `usage` é só "formato inesperado".
- **S27, o instalador executa o CLI do VS Code** (v0.3.0). O SessionStart dispara em segundo plano `code --install-extension <vsix> --force`, com o `code` achado no `PATH` e o caminho do `.vsix` validado pelo mesmo conjunto de caracteres do instalador da barra. No Windows passa por `cmd.exe /d /s /c`, com o `cmd.exe` do System32 por caminho absoluto e os dois caminhos entre aspas. O `.vsix` é montado pelo próprio plugin só com os arquivos de `vscode/`; os de versões anteriores são apagados depois de uma instalação boa. `HADOUKEN_SEM_PAINEL=1` desliga a instalação.
- **S28, `uso-oficial.json` adulterado** (v0.3.0). A leitura valida o schema (versão 1, porcentagens finitas de 0 a 100, instantes legíveis, só a chave `fable` em `modelos`). Fora disso, o arquivo vale como "sem leitura". O painel mostra só rótulos fixos e números.
- **S29, texto de outros plugins no relatório** (v0.4.0). O custo dos hooks lê transcripts com o stdout de hooks de qualquer plugin. Só saem números, o hash do comando e o nome do plugin que casa `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`; o texto nunca é guardado (o índice `indice-hooks.json` guarda só números e hashes, revalidados ao ler) nem mostrado. Conferido por teste com instrução no stdout. Os nomes aparecem como estão: um plugin instalado já é código em que o usuário confia.
- **S30, leitura repetida da barra** (v0.4.0). Com a barra rodando sem conversa (`refreshInterval`, ou a mesma leitura reenviada), um valor parado não passa por leitura nova: a idade só é renovada quando o valor muda ou o transcript da sessão foi escrito depois da última leitura. Sem transcript utilizável no stdin, vale a regra antiga (renova).
- **L1, OTLP forjado para a porta do Collector** (v0.4.0, aprendizado; um processo local manda eventos falsos para `127.0.0.1:47318`). O leitor monta cada registro do zero, com teto de 1 MiB por linha e 20 MB por leitura, e descarta instante mais de 40 dias atrás ou 5 min à frente. O que ele aprende só move o conforto dentro de limites fixos no código ou aperta a guarda; afrouxar exige `/hadouken:aprender aprovar`, que só o usuário digita. Os textos são fixos; da telemetria, só aparecem nomes de modelo e de subagente que passam por uma lista fechada de caracteres, e só no status e na sugestão de modelo, que vão ao usuário fora do contexto do Claude.
- **L2, binário do Collector trocado.** O SHA-256 do `.tar.gz` de cada plataforma é fixado no código e conferido no download; fora do hash, o arquivo é apagado e nunca extraído. O hash do binário extraído fica em `otel/bin/instalado.json` e é conferido de novo a cada subida em que o tamanho ou o mtime mudarem; fora dele, o Collector não é executado e a sessão avisa.
- **L3, vazamento de identidade para arquivo.** Duas barreiras: o Collector apaga `user.email`, `user.account_uuid`, `user.account_id`, `user.id`, `organization.id`, `workspace.host_paths` e todo `vcs.*` antes de gravar, e o leitor reconstrói só os campos que usa (modelo, effort, origem, custo, tokens, duração, resultado), sem ler `session.id`. Prompts, detalhes de ferramenta e corpos de API ficam desligados, e o `ligar` recusa se algum estiver ligado, no `env` do `settings.json` ou no ambiente, com o nome em qualquer caixa (no Windows, o nome da variável de ambiente não diferencia caixa).
- **L4, porta exposta na rede.** O Collector escuta só em `127.0.0.1`, só OTLP/HTTP, sem gRPC, sem extensões, com as métricas próprias desligadas e o log próprio só de erros. Com a porta ocupada, ele não sobe (nunca tenta outra porta) e a sessão seguinte avisa.
- **L5, `settings.json` corrompido pelo `ligar` ou pelo `desligar`, ou um deles acionado sem o usuário.** O `ligar` é em dois tempos: a prévia mostra o plano e um código de 8 hex tirado do SHA-256 dos bytes do `settings.json` junto com o plano; o `ligar <código>` recusa se o arquivo ou o plano mudou. O `desligar` também: a prévia mostra as chaves que saem do `env` e o que será apagado, com um código tirado da assinatura do `settings.json`, das chaves, do alcance (`dados`, `tudo` ou nenhum) e da pasta; o `desligar [dados|tudo] <código>` recusa se o código não confere, e a gravação recusa se o `settings.json` mudou depois da prévia. A gravação usa o mesmo gravador do instalador (sem seguir link, com teto, formato preservado, troca atômica, cópia `settings.json.bak-hadouken-<ms>`) e mexe só nas chaves do `env` `CLAUDE_CODE_ENABLE_TELEMETRY`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_METRICS_INCLUDE_ACCOUNT_UUID`, `OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_LOGS_EXPORT_INTERVAL` e `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE`; o `desligar` tira só as que ainda têm o valor que o `ligar` gravou (`otel/ligado.json`). O `ligar` recusa com conteúdo ligado ou outro endpoint OTLP, no `env` ou no ambiente, comparando o nome das chaves sem diferenciar caixa, e recusa também se uma dessas chaves já existir, em qualquer caixa, com outro valor (nunca grava uma duplicata de caixa). O comando é um hook `UserPromptExpansion` que bloqueia a expansão (sem modelo); a skill tem `disable-model-invocation: true`, uma sessão `claude -p` (entrypoint `sdk-*`) é recusada sem gravar nada, e só vale a expansão do comando digitado (a lista fechada do liberar, S10). Com outro `ligar`, outro `desligar` ou o passo de aprendizado em andamento (a trava do aprendizado), a resposta é "ocupado" e o `settings.json` não muda.
- **L6, apagar `ajustes.json` para soltar um aperto aprendido.** **Limite aceito:** sem o `ajustes.json` (ou com ele inválido, link ou acima de 64 KiB, ou com o aprendizado desligado), a guarda volta ao `config.json`, que o próprio usuário escolheu. Quem apaga o arquivo já roda como o usuário e poderia editar o `config.json` direto; o aperto aprendido nunca fica abaixo do piso de 70% nem acima do que o usuário configurou.
- **L7, a rede do aprendizado.** Dentro do aprendizado, só `src/aprendizado/baixar.js` abre conexão (teste de fronteiras pelo texto do código): um GET HTTPS do release do Collector no GitHub, com lista fixa de hosts inclusive nos redirecionamentos, teto de tamanho e de tempo, e só pelo `ligar <código>` que o usuário digitou. O Claude Code manda o OTLP só para `127.0.0.1`.
- **L8, os processos do aprendizado.** Dentro do aprendizado, só `src/aprendizado/coletor.js` cria processo: o `tar` do sistema (com cwd na pasta do binário e só o membro fixado), `tasklist`/`ps`, `taskkill` e o próprio Collector; no Windows, tudo do System32 por caminho absoluto, e sempre por `execFile`/`spawn` sem shell, com argumentos fixos. O Collector sobe desanexado, sem janela e com ambiente mínimo (sem `OTEL_*` nem segredo); o PID é conferido pelo nome do processo antes de parar; com menos de 1,5 GiB livres, não sobe. **Limite aceito:** a parada confere só o nome do processo (`otelcol-contrib`), não o caminho do binário: um arquivo de PID forjado que aponte para outro `otelcol-contrib` do mesmo usuário faz esse processo ser parado (no Windows, com a árvore dele, pelo `taskkill /t`). Quem forja o arquivo de PID já roda como o usuário e poderia parar esse processo direto.
- **K1, os plugins opcionais `hadouken-kit` e `hadouken-rea`** (v0.5.0). O hook do kit, `kit/hooks/fluxo.js`, só imprime uma constante no SessionStart (não lê stdin, arquivo, ambiente nem rede). O kit leva também as cópias fixadas da `yu-ux-web-expert` e da `graphify`; a yu-ux traz o `setup.sh` (npm com o `package-lock.json` do kit, `pip install playwright` no Python do usuário, download do Chromium) e scripts Python que rodam quando a skill os chama. A cópia da yu-ux não libera ferramenta sem pergunta além de Read, Grep e Glob: ela lê páginas de terceiros, e uma injeção no conteúdo não vira comando sem a permissão do usuário. Desde a v0.5.2, os terceiros do kit são entradas do próprio marketplace do Hadouken com o commit fixado (`sha` de 40 hex): o Claude Code instala exatamente o commit que a suíte testou. O `allowCrossMarketplaceDependenciesOn` lista só o `claude-plugins-official` (do `superpowers`). Quem sobe os `sha` é o robô semanal (`.github/scripts/kit-atualizar.mjs`, a única rede do repositório fora do plugin): ramo próprio, suíte em 3 sistemas × 3 Nodes, e só então merge rápido na `main`, tag e release pelo `GITHUB_TOKEN`. **Risco aceito:** o robô publica código de terceiros sem revisão humana; a trava é a suíte (que confere o mapa do fluxo contra as skills de cada terceiro) e o `sha` fixo. O `hadouken-rea` vem desligado. Ligado, ele lança um processo (`rea/lancar.mjs` → `npx -y rea-agents@6.1.0 mcp`, versão exata; no Windows pelo `cmd.exe /d /c` do System32), baixa o `rea-agents` do npm na primeira vez e **executa os programas que analisa com as permissões do usuário**. O cwd do `npx` é a pasta do plugin, nunca o projeto aberto: um `node_modules/rea-agents` ou um `.npmrc` plantado no repositório não entra; no Windows, `NoDefaultCurrentDirectoryInExePath=1` impede o `cmd.exe` de achar um `npx.cmd` no cwd. A fronteira "rede só em `src/aprendizado/baixar.js`, processo filho só em `src/aprendizado/coletor.js`" vale para `src/` do `hadouken` e segue intacta. O instalador de um comando (`install.sh`, `install.ps1` e `src/instalar/`) roda fora de sessão, pelo usuário no terminal. Ele abre processos filhos com argumentos fixos: o `claude` (caminho absoluto conferido pelo `caminhoSeguro`; no Windows, o `claude.cmd` só pelo `cmd.exe` do System32), o Python do usuário só para criar o venv `~/.claude/hadouken/venv` e o `pip` desse venv (`graphifyy==0.9.25`, nunca `--user`), e o `setup.sh` da yu-ux, estes com o diretório atual na casa do usuário; o código de `src/instalar*` não abre conexão (teste de fronteira). No `settings.json`, só pelo gravador da barra (backup, sem link, troca conferida), muda `extraKnownMarketplaces["claude-hadouken"]` (`autoUpdate: true`) e põe `false` nas cópias antigas dos terceiros em `enabledPlugins`. Os scripts não usam `sudo` e não leem nem gravam segredo; o texto de fora (saída do `claude`, do `winget`, do `brew`, do `pip`) não entra no resumo.

Riscos residuais da guarda (v0.4.0):

- **R1, forja pelo shell, comando ofuscado ou edição que a P5 não cobre:** escapa da P4 e da P5. A barra e os eventos tornam a forja visível; não a impedem. A P5 cobre:
  - a pasta de dados;
  - os `settings.json` e `settings.local.json` do usuário, em `~/.claude` e no `CLAUDE_CONFIG_DIR`;
  - o próprio plugin: a raiz dele e o que tiver `claude-hadouken` dentro de `plugins/` (o cache e o marketplace);
  - nos settings de projeto (`.claude/settings.json` e `.claude/settings.local.json`), o Write, o Edit e o MultiEdit que mudam o valor de `disableAllHooks`, `enabledPlugins` ou `hooks`. A P5 aplica a edição ao arquivo atual (Edit, a primeira ocorrência ou todas com `replace_all`; MultiEdit, em ordem; Write, o `content`) e compara as três chaves antes e depois. Nega também quando:
    - o texto novo ou antigo (`old_string`) traz `disableAllHooks`, `enabledPlugins`, `"hooks"` ou `claude-hadouken`;
    - um `old_string` abaixo de 40 caracteres, ou o Write, vai num arquivo que já traz uma dessas palavras;
    - o arquivo não pode ser lido (link, acima de 1 MiB);
    - a edição não se aplica (o `old_string` não está no arquivo);
    - o resultado deixa de ser JSON num arquivo com uma dessas chaves.

  O filtro `if` dos settings de projeto é ancorado com `//**/` (commit 1e69086), e assim a P5 cobre o Write, o Edit e o MultiEdit nesses arquivos também no Windows, onde o `**/` sem âncora não casava caminho absoluto (spike S13 da parte 2).

  A documentação diz que os settings são relidos durante a sessão e que o `disableAllHooks` do usuário, do projeto ou local desliga os hooks de plugin. Desde a v0.4.0, a P5 de config (o hook `ConfigChange`, abaixo) segura, na sessão em curso, a mudança de `disableAllHooks`, `enabledPlugins` ou `hooks` nos settings do usuário e do projeto, venha de onde vier. Por isso, o que escapa da P5 nesses três campos só desliga a guarda a partir da próxima sessão, que lê o arquivo mudado:
  - o Bash ou o PowerShell editando esses arquivos (por exemplo, `sed -i` no `settings.json`), na sessão em curso ou com nenhuma sessão viva (o `ConfigChange` só cobre a sessão em curso);
  - o NotebookEdit nos settings de projeto, porque a regra do conteúdo vale só para as ferramentas que trazem o texto novo;
  - uma edição com mais de 1 MiB de stdin cujo texto cru não cite `settings` nem `hadouken`, por exemplo por um link ou um nome 8.3 cujo caminho escrito não traz essas palavras (R2).

  Desligam a guarda a partir do próximo hook, porque nem a P5 nem o `ConfigChange` os cobrem:
  - fora do escopo da P5: um clone do marketplace com outro nome (a pasta em `plugins/marketplaces/` sem `claude-hadouken` no caminho) e o `plugins/installed_plugins.json`, que diz de onde o Claude Code carrega cada plugin;
  - outros diretórios de configuração, como um `CLAUDE_CONFIG_DIR` fora de `~/.claude` ou a raiz de um plugin carregado de outra pasta (`--plugin-dir`), e um plugin fora de `~/.claude/plugins`. O hook da P5 os cobre, mas o filtro `if` só leva a ele os caminhos de `~/.claude` e os `.claude/settings.json` e `.claude/settings.local.json` abaixo da pasta de trabalho. No `settings.json` de um `CLAUDE_CONFIG_DIR` absoluto, o `ConfigChange` ainda segura os três campos na sessão em curso;
  - um `HADOUKEN_HOME` fora de `~/.claude/hadouken`: o filtro `if` não leva a pasta de dados dele à P5. Na sessão manual do roteiro, com um `HADOUKEN_HOME` temporário, o `if` casou o caminho padrão, mas o hook protege a pasta de dados configurada, não a padrão, e o deny ponta a ponta não foi observável; o deny na pasta padrão fica nos testes de unidade;
  - o nome curto 8.3 de qualquer caminho protegido, que o filtro `if` não casa;
  - no Windows, o compartilhamento administrativo da própria máquina: o hook traduz `\\localhost\C$\...`, `\\127.0.0.1\C$\...`, `\\?\UNC\localhost\C$\...` e o nome da máquina para `C:\...`, mas não é confirmado que o filtro `if` o leve ao hook, e outro nome da mesma máquina (apelido de DNS, IP da rede, IPv6) não é traduzido.

  **A P5 de config (hook `ConfigChange`, v0.4.0).** No spike S13 da parte 2, cada edição externa do `.claude/settings.json` (o equivalente ao `! sed -i` do usuário) gerou um `ConfigChange` cerca de 1 s depois, com a origem e o caminho do arquivo. O hook:
  - cobre qualquer gravação no `settings.json` do usuário (`$CLAUDE_CONFIG_DIR/settings.json` quando a variável é absoluta, senão `~/.claude/settings.json`) e nos `.claude/settings.json` e `.claude/settings.local.json` do projeto, venha do shell, do usuário ou de outro programa. Só segura a mudança que toca `disableAllHooks`, `enabledPlugins` ou `hooks`; os outros campos (`model`, `permissions` e o resto) passam. O spike S13 da parte 2 mediu só os settings de projeto (`project_settings`); os settings do usuário e o local são cobertos pelo código, mas não foram medidos ao vivo;
  - não desfaz nada: o arquivo no disco fica mudado. O Claude Code mantém os settings anteriores na sessão (`decision: block`), e a próxima sessão lê o arquivo novo. Se a mudança desligou os hooks ou o plugin, a guarda fica desligada a partir da próxima sessão. É uma trava da sessão, não uma proteção do arquivo;
  - compara com uma foto tirada uma vez por sessão: no primeiro SessionStart, os três campos daqueles três arquivos vão para `config-base.json`, só em hashes, uma entrada por (sessão, caminho), com a normalização de caminho da P5, até 600 entradas e 512 KiB (as mais velhas saem primeiro). Um compact, um clear ou um resume da mesma sessão não troca a foto. O `ConfigChange` compara o arquivo atual com a foto da própria sessão (o `session_id` do stdin), nunca com a de outra: uma sessão aberta depois da mudança fotografa o arquivo novo e o aceita, e a sessão que segurou a mudança continua segurando. Um arquivo sem foto é comparado com um arquivo ausente, então um settings novo que traz `hooks` é segurado;
  - falha fechada: um arquivo que não pode ser lido agora (JSON inválido, JSONC com comentário ou vírgula sobrando, acima de 1 MiB, não é arquivo comum) tem toda mudança segurada, com o detalhe `ilegivel`, mesmo quando a foto da sessão também era ilegível. Não foi medido se o Claude Code aceita JSONC; se aceitar, um settings mantido em JSONC tem toda mudança segurada em toda sessão, até ser escrito como JSON comum. Nos settings de projeto ou local, um `ConfigChange` sem `file_path` é segurado (`sem-caminho`), e um sem `session_id` válido também (`sem-sessao`), mesmo com o arquivo igual. No settings do usuário, sem `session_id` válido, a mudança passa e grava o evento `erro` `P5:config-sessao`. O spike S13 da parte 2 viu o `session_id` no stdin, então esse caminho é defensivo;
  - falha aberta, à vista: sem pasta de dados, o hook passa calado e não cria nada (nenhuma sessão foi registrada). Um erro inesperado deixa a mudança passar e grava o evento `erro` `P5:config`, como os outros hooks (§4.5). Uma foto que falha no SessionStart grava o evento `erro` `config-foto` e não muda a linha de abertura;
  - não cobre a política gerenciada (`policy_settings`) nem as mudanças em skills.

  Comportamentos declarados da P5 de config:
  - **`/plugin`, `/hooks` e `/config` (não medido):** o spike S13 da parte 2 mediu só gravações externas. Se o Claude Code disparar o `ConfigChange` nas gravações dele mesmo, ligar ou desligar um plugin pelo `/plugin`, editar um hook pelo `/hooks` ou mudar um dos três campos pelo `/config` no meio da sessão fica segurado até a próxima sessão, com o texto do bloqueio. Uma troca de `model` e de outros campos não muda.
  - **Registro da sessão:** só sessões registradas pelo SessionStart do plugin são guardadas (o mesmo `ativas/` da P1 a P4). Apagar `ativas/<id>` pelo shell cala o hook naquela sessão.
  - **`config-base.json` forjado:** um `config-base.json` forjado pelo shell é aceito como foto (a pasta de dados, R1). As ferramentas de edição não o alcançam, porque a P5 cobre a pasta de dados.
  - **Foto ausente:** com a foto por sessão, ela só falta depois de uma corrida (dois SessionStart ao mesmo tempo: a última gravação vence, e a foto da outra sessão pode se perder), de mais de 600 entradas mais novas, ou de um relógio que voltou mais de 5 minutos (o `at` da foto fica no futuro e inválido). Sem foto, o arquivo é comparado com um ausente: falha fechada. Um `settings.json` do usuário com `enabledPlugins` segura qualquer gravação nesse arquivo na sessão, até uma troca de `model`, com o evento `config-bloqueada` `enabledPlugins`.
  - **Foto de novo depois de uma foto ausente:** uma sessão sem foto (podada, ou uma sessão velha retomada com `resume`) fotografa de novo no SessionStart seguinte, com o arquivo como está. Se ele traz uma mudança segurada antes no mesmo processo, ela vira a base e passa na gravação seguinte.
  - **`/clear` (não medido):** se o `/clear` der à conversa um `session_id` novo, ele é uma sessão nova para a foto, e uma mudança segurada antes dele passa na gravação seguinte. Só o usuário roda `/clear`. O compact mantém o `session_id`.
  - **`resume` num processo novo (não medido):** não se sabe se ele mantém o `session_id`. Se mantiver e a foto não tiver sido podada, a foto continua a velha, enquanto o processo novo carrega o arquivo do disco. Se o usuário mudou `enabledPlugins` ou `hooks` entre os dois processos, toda gravação seguinte nesse arquivo difere da foto e é segurada, até uma troca de `model`, e o texto do bloqueio diz "na próxima sessão", embora o processo em curso já tenha a mudança. Isso bloqueia a mais e nunca enfraquece a guarda; abrir uma sessão nova (não um resume) acaba com ele.
  - **Resíduos pelo shell:** apagar `ativas/<id>` ou forjar o `config-base.json`, como acima.

  **Contagem dobrada.** Com a âncora `//**/`, duas regras `if` casam o `settings.json` do usuário, e o hook da P5 roda duas vezes: cada edição grava dois eventos `arquivo-negado`, em qualquer pasta de trabalho. A negação não muda; só a contagem em "Guarda (7 dias)" dobra.

  **Liberação sem origem por evicção.** O registro guarda os 200 eventos mais novos. Se o evento `liberacao` de uma liberação ainda ativa sair do registro, a barra mostra "liberação sem origem". É falso alarme, não bypass: a liberação foi dada pelo `/hadouken:liberar` digitado.

  Excesso aceito nos settings de projeto (o usuário aplica a mudança à mão):
  - uma permissão que cite `claude-hadouken`;
  - num arquivo com uma das palavras, o Write e a troca de um trecho curto, mesmo sem mudar as três chaves;
  - a edição que o Claude Code aplicaria com as normalizações dele (aspas curvas, por exemplo) e a simulação não acha;
  - num arquivo fora do JSON estrito (comentários, vírgula sobrando), a P5 não compara as chaves: nega quando o arquivo atual ou o resultado tem uma das palavras.

  Também escapam do hook da agenda um scheduler MCP cujo nome não tenha `cron`, `schedule`, `trigger` nem `task`, e a tarefa durável gravada direto no `.claude/scheduled_tasks.json` (pelo shell ou pelas ferramentas de edição); quando ela dispara, sobra o `disable-model-invocation` da skill, que a documentação diz impedir o disparo agendado, porque na versão 2.1.286 o `command_source` é a fonte da definição do comando (`plugin` também no disparo agendado) e o hook do liberar não separa os dois por ele. O mesmo vale para o `/hadouken:aprender` (`aprovar` afrouxa a guarda, `desligar` tira o aprendizado): o hook do aprender usa a mesma lista fechada de origem e também não separa o disparo agendado do comando digitado; sobra o `disable-model-invocation` da skill. A sessão manual do roteiro não exercitou esse caso, porque o agendamento pelo `/loop` foi recusado antes (S10); ele fica declarado. A P4 é best-effort: o `if` do `hooks.json` leva a ela o `claude` e cada lançador explícito (`npx`, `node`, `bash`, `sh`, `cmd`, `pwsh`, `powershell`, no Bash e no PowerShell, e, no PowerShell, `Start-Process`), e o hook lê o comando de novo. Escapam dela (da regra fixa, que sempre nega o `claude` junto com o comando de liberação, e da negação comum, com a guarda disparada):
  - a ofuscação que monta `hadouken` em tempo de execução;
  - o nome `claude` montado em pedaços (`c=cla; ${c}ude -p ...`), sem o texto da liberação;
  - scripts e processos fora das ferramentas Bash e PowerShell (arquivo `.sh` ou `.ps1`, `npm run`);
  - o pedido lido de arquivo (`claude -p < pedido.txt`);
  - lançadores fora da lista do `if`. O `PowerShell(& *)` ficou de fora, porque a documentação não confirma que o `&` entra no texto casado (o `PowerShell(claude *)` já casa `& claude -p`, spike S9); formas como `cmd.exe` e `node.exe` não casam `Bash(cmd *)` nem `Bash(node *)`;
  - `$(claude ...)` dentro de um `git commit`: de propósito, nenhum `if` leva o `git commit` à P4 (um curinga como `Bash(*claude*)` levaria todo commit com o trailer do Claude);
  - `echo ... | bash`, `bash <<<` e `python -c`;
  - um alias `co-authored-by:` que aponte para o `claude` (com `shopt -s expand_aliases` ou um `.bashrc` lido);
  - em tese, um comando acima de 4 MiB sem `claude` nem `liberar` em todo o stdin, porque acima desse teto a P4 não lê o comando e só procura essas duas palavras. Na prática isso quase nunca passa: o stdin do hook em geral traz o `transcript_path`, com `.claude` no caminho (um `CLAUDE_CONFIG_DIR` sem "claude" no nome o tira dali), então a P4 nega o comando de lançador acima de 4 MiB (falha fechada). Quando passa, o evento `erro` P4 deixa "guarda com erro" na barra;
  - o hook que estoura o tempo (R2).

  Excesso aceito: a regra fixa da P4 nega o `git commit -m` que cita por extenso o comando de liberação. Use `git commit -F <arquivo>`.
- **R2, timeout:** hook que estoura o tempo deixa passar. O pior comando de 4 MiB que a P4 lê leva cerca de 2 a 5 s, abaixo do timeout de 10 s; numa máquina carregada, pode chegar perto dele. O stdin acima do teto (1 MiB; 4 MiB na P4) ou cortado pelo prazo de 1 s também deixa passar, e o evento `erro` com o rótulo do hook mostra "guarda com erro" na barra por 15 min. O hook da agenda falha fechado: sem o JSON inteiro, o texto lido que traga o pedido de liberação é negado, com os escapes do JSON (`\n`, `\t`, `\uXXXX` e os outros) desfeitos antes; sem o pedido, passa com o evento `erro`. A P5, acima do teto, não lê o JSON e nega quando o texto cru cita `settings` ou `hadouken`, sem diferenciar maiúsculas (como a P4 com `claude` ou `liberar`); a edição grande que não cita nenhum dos dois (uma pasta de dados num `HADOUKEN_HOME` sem `hadouken` no caminho, um plugin carregado de outra pasta, ou um link ou um nome 8.3 cujo caminho escrito não traz nenhum dos dois, mas cujo destino real é protegido: abaixo do teto a P5 resolve o caminho real, acima dele só procura no texto cru) passa com o evento `erro`. Excesso aceito: numa pasta de trabalho com `hadouken` no caminho, como o próprio repositório do plugin, toda edição acima de 1 MiB é negada, porque o `cwd` e o `transcript_path` do stdin trazem a palavra. Na P5, só `comum.js` e `base.js` entram estáticos: um deles que não carrega derruba o processo antes de qualquer decisão, com código 1, e o Claude Code trata essa saída como erro que não bloqueia: a edição passa sem o evento `erro`, fora do §4.5 da spec (que pede saída 0). O `arquivo.js` (e o que ele importa) falha fechado: sem ele, a P5 nega os settings de projeto sem conferir a mudança, continua negando a pasta de dados, os settings do usuário e o plugin, e deixa passar o resto; sem o `mensagens.js`, a negação usa um texto de reserva do próprio hook. O evento `erro` `P5:arquivo.js` só é gravado quando o `registros.js` carrega. Como ele importa o `arquivo.js`, com o `arquivo.js` quebrado a negação sai sem evento e a barra não mostra "guarda com erro".
- **R3, sessões sem guarda:** abertas antes da atualização sem `/reload-plugins`, `--bare`, plugins desligados, outras máquinas, claude.ai e o app desktop. A barra diz "sem guarda nesta sessão" onde ela roda.
- **R4:** retirado com a liberação sem código.
- **R5, limite do Fable pela leitura oficial (emendas E2 e E7):** desde a v0.3.0, o painel lê a semana do Fable pelo `/usage` oficial (`claude -p /usage`, sem modelo e sem tokens) e a grava em `uso-oficial.json`. A guarda usa essa leitura como piso quando ela tem até 15 min: 100% trava o Fable (G6), e `fable.tetoPct` (90%) zera o teto de despachos Fable (G7). Leitura velha, ausente ou fora do schema (S28) não conta; aí só valem o StopFailure (G6) e a contagem de despachos (G7). Sem sessão ativa ou com pouca RAM o painel não lê, e a leitura envelhece. A statusline segue sem campo por modelo.
- **R6, subagentes que escapam da P1:** no spike S8 da parte 2, dois caminhos abriram um subagente sem passar pela P1:
  - uma skill com `context: fork` digitada pelo usuário abre um subagente (SubagentStart) sem PreToolUse de Agent ou de Skill; só passa pelo UserPromptSubmit do prompt digitado;
  - o `SendMessage` a um subagente já terminado gera um PreToolUse de SendMessage e um SubagentStart novo, que reabre o subagente fora da P1; o hook não distingue a reabertura de um agente concluído.

  O `Workflow` (PreToolUse Workflow) e o Agent em segundo plano passam pela P1. A Skill invocada pelo modelo (ferramenta Skill) não foi testada. Os dois escapes ficam declarados, sem mudança de código: o matcher `Skill` não entra, porque bloquearia toda skill (decisão 16 do plano da parte 2).
- **Trava que se perde com o `guarda.json`:** apagar o `guarda.json` depois que a condição passou (por exemplo, a semana voltou a 50%) perde a trava do G4 que estava gravada. A guarda deriva de novo da condição do momento (spec §4.5), e ela já não dispara.
- **G7 sem reset legível:** a trava do G7 cujo reset oficial não se lê (`resetsAtMs` nulo) não tem fim até `/hadouken:liberar fable`.
- **Agentes de plugin e `Workflow`:** o frontmatter de um agente com espaço de nome (`plugin:agente`) não é lido. Sem `effort` no parâmetro do Agent nem `CLAUDE_EFFORT`, o perfil dele sai `desconhecido` e escapa das travas do Fable e do G5 (um evento registra o despacho desconhecido); G1 a G4 o travam como qualquer despacho. O `Workflow` sai sempre `desconhecido`.
- **Corrida entre sessões:** duas sessões que leem, mudam e gravam o mesmo arquivo ao mesmo tempo podem perder um registro (um despacho Fable, um limite, um modelo).
- **Janela entre `lstat` e `open`:** um arquivo trocado por um link nesse intervalo não é visto como link.
- **P5:** o `..` é colapsado antes de resolver os links, então um caminho com um link seguido de `..` pode chegar à pasta de dados sem ser reconhecido. Um sistema de arquivos sem distinção de maiúsculas no macOS não é tratado.
- **Entrypoint:** no spike S12 da parte 2, a sessão `claude -p` aberta do Bash de uma sessão do VS Code recebeu `CLAUDE_CODE_ENTRYPOINT=sdk-cli`, e o hook do liberar já a recusa pelo entrypoint (ele recusa todo valor que começa com `sdk`). O `claude-vscode` continua aceito, porque é o entrypoint do `/hadouken:liberar` digitado no VS Code; recusá-lo recusaria também o usuário. Se uma versão futura passar `claude-vscode` ao filho `-p`, a defesa é a regra fixa da P4, que nega sempre o comando Bash ou PowerShell que chama `claude` com o pedido de liberação; um comando ofuscado escapa dela (R1).
- **SessionStart dentro de subagente:** o início de sessão que roda dentro de um subagente (o compact dele chega com o `session_id` da sessão mãe) não faz nada: não registra, não reescreve os shims, não injeta linha e não grava modelo. O modelo da sessão mãe não muda; gravar o do subagente soltaria a P2 e a P3 numa sessão Fable.

**Regra de compatibilidade** (v0.2.0): dado novo vai sempre para um arquivo novo, nunca para uma chave nova num arquivo que uma versão anterior valida com formato estrito. A v0.1.0 trata um `alertas.json` com uma chave a mais como inválido e o regrava; com versões misturadas (uma sessão aberta antes da atualização segue com os hooks da versão anterior), as duas repetiriam avisos uma à outra. Por isso a memória de projeção mora no `projecao.json`, que a v0.1.0 não conhece, e o `alertas.json` mantém o formato exato da v0.1.0.

**Limite honesto:** uma skill ou um programa malicioso que já executa código como o mesmo usuário do sistema pode alterar qualquer arquivo desse usuário, inclusive o `settings.json` e o próprio plugin. Nenhum plugin impede isso. O que este plugin garante é não ampliar esse poder e desfazer, a cada sessão, adulterações dos seus shims.

## O que o plugin nunca faz

- **Rede:** sem o aprendizado ligado, o plugin não abre conexão própria. A única saída para a rede é `gh api` somente leitura: o comando é sempre `gh api <endpoint>`, sem `-f`, `-F`, `--input` nem `--method`, portanto sempre GET. Quem o chama é o relatório `/hadouken:consumo`, para os repos listados em `~/.claude/hadouken/config.json`. Se nenhum repo estiver configurado ali, ele usa o repo do remoto `origin` da pasta atual, lido localmente com `git remote get-url origin`, que não acessa a rede. São no máximo 3 repos por chamada, com cache de 15 minutos. Desde a v0.3.0, o painel do VS Code roda `claude -p /usage` (S26): quem fala com a Anthropic é o próprio Claude Code, pelo comando oficial dele, com a sua sessão. O plugin não lê a credencial, não chama endpoint nenhum e não gasta tokens: o `/usage` é comando local, sem modelo. Desde a v0.4.0, com o aprendizado ligado (opcional, desligado por padrão), há mais duas: o download único do Collector (L7) e o OTLP que o Claude Code manda ao Collector em `127.0.0.1`, que não sai da máquina (L4).
- **Telemetria:** nenhuma. Nada é enviado a nenhum serviço, nem ao autor do plugin. O aprendizado local recebe o OpenTelemetry do Claude Code só em `127.0.0.1` e o guarda filtrado na pasta de dados (L3); nada vai a serviço nenhum.
- **Tokens e credenciais:** o plugin não lê, não registra e não guarda token ou credencial de acesso. O login do GitHub pertence ao `gh`, e o ambiente do processo passa ao `gh` sem que o plugin examine os valores das variáveis. Os "tokens" do relatório são contagens de uso lidas dos transcripts. Dos transcripts, o índice guarda só o caminho relativo de cada arquivo, ids de sessão e de requisição, números, datas, modelo, effort e o nome do projeto.
- **Gravação fora de `~/.claude/hadouken/`:** o plugin só grava dentro de `~/.claude/hadouken/`, ou da pasta indicada por `HADOUKEN_HOME` quando essa variável está definida (veja "Variáveis de ambiente", abaixo). A única exceção é `~/.claude/settings.json` (ou o arquivo indicado por `HADOUKEN_SETTINGS`, quando definida), que só muda quando o comando do instalador roda com `--aplicar`, ou com `--remover` para desfazer, e nesse caso só a chave `statusLine` muda. O instalador de um comando também grava ali `extraKnownMarketplaces["claude-hadouken"]` e `false` nas cópias antigas dos terceiros em `enabledPlugins` (K1). O caminho documentado para isso é `/hadouken:instalar`, que o modelo não pode acionar e que pede confirmação explícita antes de gravar. Junto com o `settings.json`, na mesma pasta `~/.claude/`, o instalador cria um backup (`settings.json.bak-hadouken-<instante em ms>`, modo 0600; guarda os 5 mais recentes e apaga os seus mais antigos) e um temporário da troca atômica (`settings.json.hadouken-<hex>.tmp`, removido logo em seguida). Se `~/.claude/` não existir, ele a cria. A outra exceção (v0.3.0) é a extensão do painel: o CLI do VS Code a instala na pasta de extensões dele (S27). Desde a v0.4.0, o `ligar` e o `desligar` do aprendizado mudam só as chaves de telemetria do `env` do mesmo `settings.json`, com o mesmo gravador e a mesma cópia (L5).

O plugin lê, sem gravar: os transcripts em `~/.claude/projects/` (ou `$CLAUDE_CONFIG_DIR/projects`), o JSON que o Claude Code entrega à statusline e o stdin dos hooks.

## Variáveis de ambiente

O ambiente da sessão do Claude Code é confiável. Quem o controla (o `env` do `settings.json` de um projeto, direnv, um devcontainer, o shell que abriu o Claude Code) já controla `PATH` e `NODE_OPTIONS`, e com eles qualquer programa que a sessão roda; isso fica fora do escopo. As variáveis abaixo valem sempre que estão definidas, não só nos testes do plugin, e de caminho só aceitam um caminho absoluto completo (no Windows, com letra de unidade ou UNC):

- `HADOUKEN_HOME`: a pasta de dados, no lugar de `~/.claude/hadouken/`; tudo o que o plugin grava, inclusive os shims em `bin/`, vai para ela. Definida com qualquer outro valor (relativo, vazio, só espaços; no Windows, também `\pasta` ou `C:pasta`), o plugin fica sem pasta de dados: a barra e os hooks não gravam nada, o `/hadouken:consumo` só lê, o instalador recusa com o motivo `pasta-dados-invalida`, e a pasta padrão nunca é usada no lugar. Antes de gravar, o instalador mostra a pasta e de onde ela vem (`pastaDados` e `origemPastaDados`), e a skill `/hadouken:instalar` avisa quando ela vem desta variável: a barra gravada no `settings.json` aponta para essa pasta em todo projeto. O mesmo vale para a recusa quando o `settings.json` é um link: a chave `manual` que ela oferece para colar à mão aponta para essa pasta.
- `HADOUKEN_SETTINGS`: o `settings.json` que o instalador edita, no lugar de `<CLAUDE_CONFIG_DIR>/settings.json` ou `~/.claude/settings.json`. Definida com qualquer outro valor, o instalador recusa com o motivo `hadouken-settings-invalido` e nunca cai no arquivo padrão.
- `HADOUKEN_TESTE_GH`: só o valor exato `ausente` tem efeito: o `/hadouken:consumo` não chama o `gh`, e a seção do GitHub sai indisponível. Os testes do plugin a usam. Qualquer outro valor é ignorado, e nenhum valor dela vira programa: o `gh` é sempre o achado no `PATH`, por caminho absoluto.
- `HADOUKEN_SEM_PAINEL`: com o valor exato `1`, o SessionStart não instala nem atualiza a extensão do painel no VS Code (v0.3.0). Se a variável estiver no ambiente do próprio VS Code, a extensão já instalada também para de rodar o `/usage`. Para tirar o painel de vez: `code --uninstall-extension gariolilabs.claude-hadouken-painel` e recarregar a janela.

## Scope

The plugin code in this repository: `src/`, `hooks/`, `skills/`, `.claude-plugin/`, `bench/`, `.github/`, `kit/` (hadouken-kit) and `rea/` (hadouken-rea). Claude Code, `gh`, Node.js and GitHub have their own channels and are out of scope.

The plugin's guarantee (spec, section 8.1): no data it reads ever becomes executed code, a shell command, an arbitrary API path, a terminal sequence or an instruction carrying the plugin's authority in Claude's context. This covers the files in `~/.claude/hadouken/`, transcripts, the status line JSON, hook stdin, GitHub responses and skill arguments.

Threat model summary:

- **S1, tampered data file** (`estado.json`, `alertas.json`, `projecao.json`, `config.json`, `historico.jsonl`, indexes) used to inject text into Claude's context through a hook. Injected text is built only from validated finite numbers and labels from fixed lists in the code. A file that fails its schema reads as "sem leitura" (no reading). Since v0.2.0 (spec §12.7): the reading history in `estado.json` is validated point by point (at most 90 points, `at` between 3 hours ago and 5 minutes ahead, percentages from 0 to 100; the rest is dropped, and a history that is not a list becomes an empty list); the forecast only comes out with at least 3 points over 6 minutes, a positive finite slope and an instant before the reset; the active session count only counts valid ids, never goes above 50 and only shows as a whole number; the projection memory lives in a file of its own, `projecao.json`, which keeps at most 256 sessions, only accepts valid ids and bands from the fixed list, is written atomically and only when it changes, and is never created empty; hostile content in it (a file above 1 MB, keys such as `__proto__` or `constructor`, wrong types, a band outside the list, a reset instant that is not a finite number between 0 and 10¹¹ s, instruction text) makes the file count as empty (the safe side: the current band is announced again) until it is rewritten clean; and the projection notice carries only validated numbers and fixed text.
- **S2, malicious text** in transcripts, project names, session ids, model, effort, repos or GitHub fields shown by `/consumo`. A single sanitiser (`sanear`) strips control characters, ANSI/OSC sequences, `|`, backticks and line breaks, and caps the text at 64 characters. Effort is accepted only from a fixed list, and the report states that these fields are data, not instructions. The model's short name (`Opus 5.5`, v0.2.0) only comes from a sanitised name matching a fixed pattern anchored at both ends; it is display only and changes no sums, keys or `--json`. The "open sessions in the last hour" section (v0.2.0) uses the same cleaning as the other tables, and the markdown revalidates the JSON `sessoesAbertas` list item by item before showing it.
- **S3, terminal sequences** (ANSI/OSC, such as fake links or titles) reaching the status bar through `model.display_name` or another field. All external text goes through `sanear` before it is printed; the only ANSI sequences in the bar are the fixed colours in the code. External names also lose the glyphs the bar draws (`│`, `·`, `↻` and, since v0.2.0, `▰`, `▱`, `┃` and `→`), so no name can forge a separator, a bar, the pace mark or a forecast; the report's limits panel holds only validated numbers and labels from the code.
- **S4, shell injection through the arguments of `/hadouken:consumo`.** The skill never forwards `$ARGUMENTS`: it runs one of two fixed commands, with or without `--json`, and the CLI ignores any other argument.
- **S5, malicious repo in `config.json`** (for example `../../user` or extra arguments). Only `owner/repo` matching `^[A-Za-z0-9-]{1,39}/[A-Za-z0-9._-]{1,100}$`, without `..`, is accepted. `gh` is called through `execFile`, never through a shell.
- **S6, tampered shim** in `~/.claude/hadouken/bin/` to run other code. The SessionStart hook rewrites the shims on every session from their expected content, and the shims read nothing from outside.
- **S7, installer triggered by another skill or by the model** without the user knowing. `/hadouken:instalar` has `disable-model-invocation: true`, asks for explicit confirmation before writing and writes only the `statusLine` key, with a backup.
- **S8, supply chain.** Zero dependencies; CI with `permissions: contents: read`, actions pinned to commit SHAs and weekly Dependabot updates.
- **S9, huge or malformed file** meant to stall a hook or the bar. Reads have size limits (state files up to 1 MB; a transcript line above 5 MB is skipped), hooks have deadlines and always exit with code 0.
- **S10, the model loads `/hadouken:liberar`** through the Skill tool. The skill has `disable-model-invocation: true` and an inert body, which only says that nothing was released. Every release happens in the UserPromptExpansion hook, never in the body. Nor does the model release through a scheduled task (`CronCreate`), the next turn of a `/loop` (`ScheduleWakeup`) or a routine (`RemoteTrigger`): the agenda hook denies at PreToolUse, always, a call carrying the release request in any text field; the documentation says that `disable-model-invocation` stops a scheduled fire from running the skill; and the release hook only accepts the expansion of the typed command (a closed list: `command_source` `plugin` and `expansion_type` `slash_command`), refusing and recording any other origin. In the manual script session (Claude Code 2.1.285 to 2.1.287), CronCreate and ScheduleWakeup carrying `/hadouken:liberar 2h` were denied at PreToolUse, with the `liberacao-recusada` event and the tool's name, and `/loop 1m /hadouken:liberar 2h` was already denied at scheduling (CronCreate): nothing was scheduled or fired, and there was no `liberacao.json`. Per spike S6 of part 2, a cron or `/loop` fire reaches UserPromptSubmit like a typed prompt, with no marker (see S22 and S23). A durable task written straight into `.claude/scheduled_tasks.json` was not exercised, because the scheduling was refused first; it stays in R1. Since local learning (v0.4.0), the agenda hook denies a call carrying `/hadouken:aprender` (`hadouken:aprender`, or `/aprender` as a word) the same way, because `aprovar` loosens the guard and `desligar` turns learning off; the deny text names both commands, and the aprender hook uses the same closed origin list (L5).
- **S11, the model opens a `claude -p` session to release itself.** The hook refuses the release when `CLAUDE_CODE_ENTRYPOINT` points to `-p` or the SDK, and P4 denies `claude ...` through Bash and PowerShell while the guard is tripped. The entrypoint signal can be forged; this is a declared limit (R1).
- **S12, S18 and S19** do not apply: the release uses no code (decision D4, option C, 2026-09-29).
- **S13, forging `liberacao.json` or deleting `guarda.json` through the edit tools.** P5 denies Write, Edit, MultiEdit and NotebookEdit in the data folder, always. It also always denies them on the user's `settings.json` and `settings.local.json` and on the plugin itself; in project settings, it denies the edit that touches hooks or plugins (R1). The path is resolved to the real path, with `..`, Windows case and links. Claude Code's `if` filter does not match the 8.3 short name or a `HADOUKEN_HOME` outside `~/.claude/hadouken` (R1). For project settings, the `if` has been anchored with `//**/` since commit 1e69086: in spike S13 of part 2, the unanchored `**/` did not match an absolute path on Windows, and with the anchor the edit was denied end to end (`P5:settings-projeto`). Two `if` rules match the user's `settings.json`, so each edit of it records two `arquivo-negado` events; the deny is the same, only the count doubles.
- **S14, forging through the shell** (R1). A process of the same user writes wherever the user writes. Mitigations: P4, the prohibition in the block text, the bar showing every release (with "liberação sem origem" when the event is missing) and "guarda desligada", and the event log. Since v0.4.0, the config P5 (the `ConfigChange` hook, R1) holds, for the current session, a change to `disableAllHooks`, `enabledPlugins` or `hooks` in settings made through the shell.
- **S15, loosening `config.json`.** A lock does not drop on a configuration change; only a release lifts it.
- **S16, hostile or huge JSON in the new files** (`guarda.json`, `liberacao.json`, `modelos.json`, `limites-atingidos.json`, `despachos-fable.json`, `guarda-eventos.json`). Reads use `lstat` (a symbolic link is invalid), a byte cap and rebuild only the known fields. An unreadable `guarda.json` counts as a tripped guard; an unreadable `liberacao.json` counts as no release.
- **S17, hostile text reaching Claude through the guard's messages** (model name, agent name, limit text, release argument). Every message is a fixed template, filled with numbers and labels from the code. The StopFailure text is only classified, and the release argument only goes through a closed grammar.
- **S20, a hook that runs out of time** lets the dispatch through (R2). The short path is measured in the bench; blocking hooks have a 10 s timeout.
- **S21, a race between sessions writing the lock.** Locks are merged and renamed atomically; a lost write comes back at the next evaluation.
- **S22 and S23, the guard locking itself out or losing work in progress.** P2 lets `/hadouken:...` through, and the automatic `<task-notification>` turn, which delivers the result of a background subagent. Per spike S6 of part 2, cron and `/loop` fires reach UserPromptSubmit with the same keys as a typed prompt, with no marker. P2 treats them as an ordinary prompt: in a Fable session with the guard tripped, the fire is blocked (decision 15 of the part 2 plan); outside Fable it passes. P1 and P3 still apply in the fired turn. R3 does not change.
- **S24, privacy.** The guard modules import no network module and no `child_process` (checked by a test), and the new files keep only numbers, times, validated ids and labels.
- **S25, usage credits after the Fable limit.** G6 is only lifted by the `fable` scope of the release, which warns that Fable may consume credits.
- **S26, the panel runs `claude`** (v0.3.0). To read `/usage`, the panel runs `claude -p /usage` in lean mode, without plugins, MCP, hooks or session persistence. The executable is looked up only in `~/.local/bin/` and the `PATH` directories (on Windows, only `claude.exe`, never `.cmd` or `.bat`) and called with `execFile`, without a shell. Arguments are fixed, output is capped at 64 KiB and time at 30 s. At the deadline the plugin kills the whole process tree (on Windows, `taskkill /t /f` from System32), and the next read waits 15 min, as after any failure (unexpected format, error). Only numbers leave the output, through anchored regexes. If the result shows a cost (`num_turns` or `total_cost_usd` other than zero, or missing), reading stops for 24 h. With zero turns and zero cost, a result that does not come from the `usage` command is only "unexpected format".
- **S27, the installer runs the VS Code CLI** (v0.3.0). SessionStart starts `code --install-extension <vsix> --force` in the background, with `code` found on `PATH` and the `.vsix` path checked against the same character set as the status bar installer. On Windows it goes through `cmd.exe /d /s /c`, with `cmd.exe` from System32 by absolute path and both paths quoted. The plugin builds the `.vsix` itself, only from the files in `vscode/`; those of earlier versions are deleted after a successful install. `HADOUKEN_SEM_PAINEL=1` turns installation off.
- **S28, tampered `uso-oficial.json`** (v0.3.0). Reading validates the schema (version 1, finite percentages from 0 to 100, readable instants, only the `fable` key in `modelos`). Anything else reads as "no reading". The panel shows only fixed labels and numbers.
- **S29, other plugins' text in the report** (v0.4.0). The hook cost section reads transcripts carrying the stdout of any plugin's hooks. Only numbers, the command's hash and a plugin name matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` come out; the text is never stored (the `indice-hooks.json` index keeps only numbers and hashes, revalidated on read) or shown. Checked by a test with an instruction in stdout. Names show as they are: an installed plugin is already code the user trusts.
- **S30, the status bar's repeated reading** (v0.4.0). With the bar running without conversation (`refreshInterval`, or the same reading sent again), a value that has not moved does not pass for a new reading: its age is renewed only when the value changes or the session transcript was written after the last reading. Without a usable transcript in stdin, the old rule applies (it renews).
- **L1, forged OTLP sent to the Collector port** (v0.4.0, learning; a local process sends fake events to `127.0.0.1:47318`). The reader rebuilds every record from scratch, capped at 1 MiB per line and 20 MB per read, and drops instants more than 40 days old or 5 min ahead. What it learns can only move comfort settings within limits fixed in the code or tighten the guard; loosening requires `/hadouken:aprender aprovar`, which only the user types. Texts are fixed; from the telemetry, only model and subagent names that pass a closed character list show up, and only in the status and in the model suggestion, which go to the user outside Claude's context.
- **L2, swapped Collector binary.** The SHA-256 of each platform's `.tar.gz` is pinned in the code and checked on download; on a mismatch the file is deleted and never extracted. The extracted binary's hash is kept in `otel/bin/instalado.json` and checked again on every start where its size or mtime changed; on a mismatch the Collector is not run and the session warns.
- **L3, identity leak into a file.** Two barriers: the Collector deletes `user.email`, `user.account_uuid`, `user.account_id`, `user.id`, `organization.id`, `workspace.host_paths` and every `vcs.*` before writing, and the reader rebuilds only the fields it uses (model, effort, origin, cost, tokens, duration, outcome), never reading `session.id`. Prompts, tool details and API bodies stay off, and `ligar` refuses if any of them is on, in the `env` of `settings.json` or in the environment, with the name in any letter case (on Windows, environment variable names are case-insensitive).
- **L4, port exposed to the network.** The Collector listens only on `127.0.0.1`, OTLP/HTTP only, with no gRPC, no extensions, its own metrics off and its own log at error level only. If the port is busy it does not start (it never tries another port) and the next session warns.
- **L5, `settings.json` corrupted by `ligar` or `desligar`, or either one triggered without the user.** `ligar` has two steps: the preview shows the plan and an 8-hex code taken from the SHA-256 of the `settings.json` bytes together with the plan; `ligar <code>` refuses if the file or the plan changed. So does `desligar`: the preview shows the keys that leave the `env` and what will be deleted, with a code taken from the `settings.json` signature, the keys, the scope (`dados`, `tudo` or none) and the folder; `desligar [dados|tudo] <code>` refuses if the code does not match, and the write refuses if `settings.json` changed after the preview. Writing uses the installer's writer (no link following, size cap, format kept, atomic swap, `settings.json.bak-hadouken-<ms>` backup) and touches only the `env` keys `CLAUDE_CODE_ENABLE_TELEMETRY`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_METRICS_INCLUDE_ACCOUNT_UUID`, `OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_LOGS_EXPORT_INTERVAL` and `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE`; `desligar` removes only those that still hold the value `ligar` wrote (`otel/ligado.json`). `ligar` refuses with content switched on or another OTLP endpoint, in the `env` or in the environment, matching key names regardless of letter case, and also refuses if one of those keys already exists, in any letter case, with another value (it never writes a case duplicate). The command is a `UserPromptExpansion` hook that blocks the expansion (no model); the skill has `disable-model-invocation: true`, a `claude -p` session (`sdk-*` entrypoint) is refused without writing anything, and only the expansion of the typed command counts (the release's closed list, S10). With another `ligar`, another `desligar` or the learning step in progress (the learning lock), the answer is "busy" and `settings.json` does not change.
- **L6, deleting `ajustes.json` to release a learned tightening.** **Accepted limit:** without `ajustes.json` (or with it invalid, a link or above 64 KiB, or with learning off) the guard falls back to `config.json`, which the user chose. Whoever deletes the file already runs as the user and could edit `config.json` directly; a learned tightening never goes below the 70% floor nor above what the user configured.
- **L7, learning's network access.** Within learning, only `src/aprendizado/baixar.js` opens a connection (boundary test over the source text): an HTTPS GET of the Collector release on GitHub, with a fixed host list also for redirects, size and time caps, and only through the `ligar <code>` the user typed. Claude Code sends OTLP only to `127.0.0.1`.
- **L8, learning's processes.** Within learning, only `src/aprendizado/coletor.js` creates processes: the system `tar` (cwd in the binary folder, only the pinned member), `tasklist`/`ps`, `taskkill` and the Collector itself; on Windows everything comes from System32 by absolute path, always through `execFile`/`spawn` without a shell, with fixed arguments. The Collector starts detached, without a window and with a minimal environment (no `OTEL_*`, no secrets); the PID is checked against the process name before stopping it; with less than 1.5 GiB free it does not start. **Accepted limit:** stopping checks only the process name (`otelcol-contrib`), not the binary's path: a forged PID file pointing at another `otelcol-contrib` process of the same user gets that process stopped (on Windows, with its tree, through `taskkill /t`). Whoever forges the PID file already runs as the user and could stop that process directly.
- **K1, the optional `hadouken-kit` and `hadouken-rea` plugins** (v0.5.0). The kit's hook, `kit/hooks/fluxo.js`, only prints a constant at SessionStart (it reads no stdin, file, environment or network). The kit also carries the pinned copies of `yu-ux-web-expert` and `graphify`; yu-ux brings `setup.sh` (npm with the kit's `package-lock.json`, `pip install playwright` in the user's Python, the Chromium download) and Python scripts that run when the skill calls them. The yu-ux copy grants no tool without asking beyond Read, Grep and Glob: it reads third-party pages, and an injection in the content does not become a command without the user's permission. Since v0.5.2, the kit's third parties are entries in hadouken's own marketplace with a pinned commit (40-hex `sha`): Claude Code installs exactly the commit the suite tested. `allowCrossMarketplaceDependenciesOn` lists only `claude-plugins-official` (for `superpowers`). The `sha` values are bumped by the weekly robot (`.github/scripts/kit-atualizar.mjs`, the repository's only network code outside the plugin): its own branch, the suite on 3 systems × 3 Node versions, and only then a fast-forward to `main`, a tag and a release through `GITHUB_TOKEN`. **Accepted risk:** the robot publishes third-party code without human review; the safeguards are the suite (which checks the flow map against each third party's skills) and the pinned `sha`. `hadouken-rea` ships disabled. Once enabled, it starts a process (`rea/lancar.mjs` → `npx -y rea-agents@6.1.0 mcp`, exact version; on Windows through System32's `cmd.exe /d /c`), downloads `rea-agents` from npm the first time and **runs the programs it analyzes with the user's permissions**. The `npx` working directory is the plugin folder, never the open project: a `node_modules/rea-agents` or `.npmrc` planted in the repository does not come in; on Windows, `NoDefaultCurrentDirectoryInExePath=1` keeps `cmd.exe` from finding an `npx.cmd` in the working directory. The boundary "network only in `src/aprendizado/baixar.js`, child processes only in `src/aprendizado/coletor.js`" applies to `hadouken`'s `src/` and stays intact. The one-command installer (`install.sh`, `install.ps1` and `src/instalar/`) runs outside any session, by the user in the terminal. It starts child processes with fixed arguments: `claude` (absolute path checked by `caminhoSeguro`; on Windows, `claude.cmd` only through System32's `cmd.exe`), the user's Python only to create the `~/.claude/hadouken/venv` venv and that venv's `pip` (`graphifyy==0.9.25`, never `--user`), and yu-ux's `setup.sh`, these with the current directory set to the user's home; the code in `src/instalar*` opens no connection (boundary test). In `settings.json`, only through the bar's writer (backup, no links, checked swap), it changes `extraKnownMarketplaces["claude-hadouken"]` (`autoUpdate: true`) and sets the old third-party copies to `false` in `enabledPlugins`. The scripts use no `sudo` and read or write no secret; outside text (output of `claude`, `winget`, `brew`, `pip`) never reaches the summary.

Residual risks of the guard (v0.4.0):

- **R1, forging through the shell, an obfuscated command or an edit P5 does not cover:** escapes P4 and P5. The bar and the events make the forgery visible; they do not prevent it. P5 covers:
  - the data folder;
  - the user's `settings.json` and `settings.local.json`, in `~/.claude` and in `CLAUDE_CONFIG_DIR`;
  - the plugin itself: its root, and anything with `claude-hadouken` inside `plugins/` (the cache and the marketplace);
  - in project settings (`.claude/settings.json` and `.claude/settings.local.json`), a Write, Edit or MultiEdit that changes the value of `disableAllHooks`, `enabledPlugins` or `hooks`. P5 applies the edit to the current file (Edit: the first occurrence, or all of them with `replace_all`; MultiEdit: in order; Write: the `content`) and compares the three keys before and after. It also denies when:
    - the new or old text (`old_string`) carries `disableAllHooks`, `enabledPlugins`, `"hooks"` or `claude-hadouken`;
    - an `old_string` under 40 characters, or a Write, targets a file that already carries one of those words;
    - the file cannot be read (a link, over 1 MiB);
    - the edit does not apply (the `old_string` is not in the file);
    - the result stops being JSON in a file that has one of those keys.

  The `if` filter for project settings is anchored with `//**/` (commit 1e69086), so P5 covers Write, Edit and MultiEdit on those files on Windows too, where the unanchored `**/` did not match an absolute path (spike S13 of part 2).

  The documentation says settings are reloaded during the session, and that `disableAllHooks` in user, project or local settings turns plugin hooks off. Since v0.4.0, the config P5 (the `ConfigChange` hook, below) holds, for the current session, a change to `disableAllHooks`, `enabledPlugins` or `hooks` in user and project settings, wherever it comes from. So whatever escapes P5 on those three fields turns the guard off only from the next session on, which reads the changed file:
  - Bash or PowerShell editing those files (for example, `sed -i` on `settings.json`), in the current session or with no live session (`ConfigChange` only covers the current session);
  - NotebookEdit on project settings, because the content rule only covers the tools that carry the new text;
  - an edit with more than 1 MiB of stdin whose raw text names neither `settings` nor `hadouken`, for example through a link or an 8.3 name whose written path carries neither word (R2).

  These turn the guard off from the next hook on, because neither P5 nor `ConfigChange` covers them:
  - out of P5's scope: a marketplace clone under another name (the folder in `plugins/marketplaces/` without `claude-hadouken` in its path) and `plugins/installed_plugins.json`, which tells Claude Code where it loads each plugin from;
  - other configuration folders, such as a `CLAUDE_CONFIG_DIR` outside `~/.claude` or the root of a plugin loaded from another folder (`--plugin-dir`), and a plugin outside `~/.claude/plugins`. The P5 hook covers them, but the `if` filter only sends it the paths under `~/.claude` and the `.claude/settings.json` and `.claude/settings.local.json` files below the working folder. On the `settings.json` of an absolute `CLAUDE_CONFIG_DIR`, `ConfigChange` still holds the three fields for the current session;
  - a `HADOUKEN_HOME` outside `~/.claude/hadouken`: the `if` filter does not send its data folder to P5. In the manual script session, with a temporary `HADOUKEN_HOME`, the `if` matched the default path, but the hook protects the configured data folder, not the default one, and the end-to-end deny could not be observed; the deny on the default folder stays in the unit tests;
  - the 8.3 short name of any protected path, which the `if` filter does not match;
  - on Windows, the machine's own administrative share: the hook maps `\\localhost\C$\...`, `\\127.0.0.1\C$\...`, `\\?\UNC\localhost\C$\...` and the machine name to `C:\...`, but it is not confirmed that the `if` filter sends such a path to the hook, and another name for the same machine (a DNS alias, the LAN IP, IPv6) is not mapped.

  **The config P5 (`ConfigChange` hook, v0.4.0).** In spike S13 of part 2, each external edit of `.claude/settings.json` (the equivalent of the user's `! sed -i`) produced a `ConfigChange` about 1 s later, with the source and the file path. The hook:
  - covers any write to the user's `settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that variable is absolute, otherwise `~/.claude/settings.json`) and to the project's `.claude/settings.json` and `.claude/settings.local.json`, whether it comes from the shell, the user or another program. It only holds a change that touches `disableAllHooks`, `enabledPlugins` or `hooks`; other fields (`model`, `permissions` and the rest) pass. Spike S13 of part 2 measured only the project settings (`project_settings`); the user and local settings are covered by the code but were not measured live;
  - undoes nothing: the file on disk stays changed. Claude Code keeps the session's previous settings (`decision: block`), and the next session reads the new file. If the change turned hooks or the plugin off, the guard is off from the next session on. It is a hold for the session, not a protection of the file;
  - compares with a photo taken once per session: at the first SessionStart, the three fields of those three files go into `config-base.json`, as hashes only, one entry per (session, path), with P5's path normalisation, at most 600 entries and 512 KiB (the oldest leave first). A compact, clear or resume of the same session does not replace the photo. `ConfigChange` compares the current file with the photo of its own session (the stdin `session_id`), never another session's: a session opened after the change photographs the new file and accepts it, and the session that held the change keeps holding it. A file with no photo is compared with an absent file, so a new settings file carrying `hooks` is held;
  - fails closed: a file that cannot be read now (invalid JSON, JSONC with a comment or a trailing comma, over 1 MiB, not a regular file) has every change held, with detail `ilegivel`, even when the session's photo was unreadable too. Whether Claude Code accepts JSONC was not measured; if it does, a settings file kept in JSONC has every change held in every session, until it is written as plain JSON. In project or local settings, a `ConfigChange` without `file_path` is held (`sem-caminho`), and so is one without a valid `session_id` (`sem-sessao`), even when the file did not change. In the user's settings, without a valid `session_id`, the change passes and records the `erro` event `P5:config-sessao`. Spike S13 of part 2 saw a `session_id` in stdin, so this path is defensive;
  - fails open, visibly: without a data folder, the hook passes silently and creates nothing (no session was ever registered). An unexpected error lets the change through and records the `erro` event `P5:config`, like the other hooks (§4.5). A photo that fails at SessionStart records the `erro` event `config-foto` and does not change the opening line;
  - does not cover managed policy (`policy_settings`) or skill changes.

  Declared behaviour of the config P5:
  - **`/plugin`, `/hooks` and `/config` (not measured):** spike S13 of part 2 measured external writes only. If Claude Code fires `ConfigChange` for its own writes, turning a plugin on or off with `/plugin`, editing a hook with `/hooks` or changing one of the three fields with `/config` during a session is held until the next session, with the block text. A change to `model` and other fields is unaffected.
  - **Session registration:** only sessions registered by the plugin's SessionStart are guarded (the same `ativas/` as P1 to P4). Deleting `ativas/<id>` through the shell silences the hook for that session.
  - **Forged `config-base.json`:** a `config-base.json` forged through the shell is trusted as the photo (the data folder, R1). The edit tools cannot reach it, because P5 covers the data folder.
  - **Missing photo:** with the photo per session, it is only missing after a race (two SessionStarts at the same moment: the last write wins, and the other session's photo can be lost), after more than 600 newer entries, or after a clock that moved back more than 5 minutes (the photo's `at` reads as future and invalid). Without a photo, the file is compared with an absent one: fail-closed. A user `settings.json` that has `enabledPlugins` holds any write to that file in the session, even a `model` change, with the `config-bloqueada` event `enabledPlugins`.
  - **Photo again after a missing photo:** a session with no photo (pruned, or an old session resumed with `resume`) photographs again at its next SessionStart, with the file as it is then. If it carries a change held earlier in the same process, that change becomes the base and passes on the next write.
  - **`/clear` (not measured):** if `/clear` gives the conversation a new `session_id`, it is a new session for the photo, and a change held before it passes on the next write. Only the user can run `/clear`. Compact keeps the `session_id`.
  - **`resume` in a new process (not measured):** it is unknown whether it keeps the `session_id`. If it does and the photo was not pruned, the photo stays the old one, while the new process loads the file from disk. If the user changed `enabledPlugins` or `hooks` between the two processes, every later write to that file differs from the photo and is held, even a `model` change, and the block text says "na próxima sessão" (in the next session) although the running process already has the change. It over-blocks and never weakens the guard; opening a new session (not a resume) ends it.
  - **Residue through the shell:** deleting `ativas/<id>` or forging `config-base.json`, as above.

  **Double count.** With the `//**/` anchor, two `if` rules match the user's `settings.json`, and the P5 hook runs twice: each edit records two `arquivo-negado` events, in any working folder. The deny does not change; only the count in "Guarda (7 dias)" doubles.

  **Release without origin through eviction.** The log keeps the 200 newest events. If the `liberacao` event of a release that is still active drops out of the log, the bar shows "liberação sem origem". It is a false alarm, not a bypass: the release was given by the typed `/hadouken:liberar`.

  Accepted over-deny in project settings (the user applies the change by hand):
  - a permission that names `claude-hadouken`;
  - in a file with one of those words, a Write or the replacement of a short stretch, even when the three keys do not change;
  - an edit Claude Code would apply with its own normalisation (curly quotes, for example) that the simulation does not find;
  - in a file outside strict JSON (comments, a trailing comma), P5 does not compare the keys: it denies when the current file or the result carries one of those words.

  These also escape the agenda hook: an MCP scheduler whose name has none of `cron`, `schedule`, `trigger` or `task`, and a durable task written straight into `.claude/scheduled_tasks.json` (through the shell or the edit tools); when it fires, what is left is the skill's `disable-model-invocation`, which the documentation says stops a scheduled fire, because on version 2.1.286 `command_source` is the source of the command's definition (`plugin` for a scheduled fire too) and the release hook cannot tell the two apart by it. The same holds for `/hadouken:aprender` (`aprovar` loosens the guard, `desligar` turns learning off): the aprender hook uses the same closed origin list and equally cannot tell a scheduled fire from the typed command; what is left is the skill's `disable-model-invocation`. The manual script session did not exercise this case, because the `/loop` scheduling was refused first (S10); it stays declared. P4 is best-effort: the `if` in `hooks.json` sends it `claude` and each explicit launcher (`npx`, `node`, `bash`, `sh`, `cmd`, `pwsh`, `powershell`, in Bash and in PowerShell, and, in PowerShell, `Start-Process`), and the hook reads the command again. These escape it (the fixed rule, which always denies `claude` together with the release command, and the ordinary denial while the guard is tripped):
  - obfuscation that builds `hadouken` at run time;
  - the `claude` name built from pieces (`c=cla; ${c}ude -p ...`), without the release text;
  - scripts and processes outside the Bash and PowerShell tools (a `.sh` or `.ps1` file, `npm run`);
  - a request read from a file (`claude -p < pedido.txt`);
  - launchers not in the `if` list. `PowerShell(& *)` was left out, because the documentation does not confirm that `&` is part of the matched text (`PowerShell(claude *)` already matches `& claude -p`, spike S9); forms such as `cmd.exe` and `node.exe` do not match `Bash(cmd *)` or `Bash(node *)`;
  - `$(claude ...)` inside a `git commit`: on purpose, no `if` sends `git commit` to P4 (a wildcard such as `Bash(*claude*)` would send every commit carrying Claude's trailer);
  - `echo ... | bash`, `bash <<<` and `python -c`;
  - an alias `co-authored-by:` that points to `claude` (with `shopt -s expand_aliases` or a `.bashrc` that gets read);
  - in principle, a command above 4 MiB with neither `claude` nor `liberar` anywhere in stdin, because above that cap P4 does not read the command and only looks for those two words. In practice it almost never gets through: the hook's stdin usually carries `transcript_path`, with `.claude` in the path (a `CLAUDE_CONFIG_DIR` without "claude" in its name moves it elsewhere), so P4 denies the launcher command above 4 MiB (fail-closed). When it does get through, the `erro` P4 event leaves "guarda com erro" in the bar;
  - a hook that runs out of time (R2).

  Accepted over-deny: P4's fixed rule denies a `git commit -m` that spells out the release command. Use `git commit -F <file>`.
- **R2, timeout:** a hook that runs out of time lets the call through. The worst 4 MiB command P4 reads takes about 2 to 5 s, under the 10 s timeout; on a loaded machine it can come close to it. Stdin above the cap (1 MiB; 4 MiB for P4) or cut by the 1 s deadline also lets the call through, and the `erro` event with the hook's label shows "guarda com erro" in the bar for 15 min. The agenda hook fails closed: without the whole JSON, text that was read and carries the release request is denied, with the JSON escapes (`\n`, `\t`, `\uXXXX` and the rest) decoded first; without the request, the call passes with the `erro` event. Above the cap, P5 does not read the JSON and denies when the raw text names `settings` or `hadouken`, case-insensitively (as P4 does with `claude` or `liberar`); a large edit that names neither (a data folder in a `HADOUKEN_HOME` without `hadouken` in its path, a plugin loaded from another folder, or a link or 8.3 name whose written path carries neither word but whose real target is protected: under the cap P5 resolves the real path, above it it only searches the raw text) passes with the `erro` event. Accepted over-deny: in a working folder with `hadouken` in its path, such as the plugin's own repository, every edit above 1 MiB is denied, because the stdin's `cwd` and `transcript_path` carry the word. In P5, only `comum.js` and `base.js` are static imports: if either fails to load, the process dies before any decision, with exit code 1, and Claude Code treats that exit as a non-blocking error: the edit goes through without the `erro` event, outside the spec's §4.5 (which asks for exit 0). `arquivo.js` (and what it imports) fails closed: without it, P5 denies project settings without checking the change, still denies the data folder, the user's settings and the plugin, and lets the rest through; without `mensagens.js`, the deny uses a reserve text from the hook itself. The `erro` event `P5:arquivo.js` is recorded only when `registros.js` loads. Because it imports `arquivo.js`, a broken `arquivo.js` means the deny goes out without an event, and the bar does not show "guarda com erro".
- **R3, sessions without the guard:** opened before the update without `/reload-plugins`, `--bare`, plugins turned off, other machines, claude.ai and the desktop app. The bar says "sem guarda nesta sessão" wherever it runs.
- **R4:** withdrawn with the code-free release.
- **R5, Fable limit from the official reading (amendments E2 and E7):** since v0.3.0, the panel reads the Fable week through the official `/usage` (`claude -p /usage`, no model and no tokens) and writes it to `uso-oficial.json`. The guard uses that reading as a floor while it is at most 15 min old: 100% locks Fable (G6), and `fable.tetoPct` (90%) sets the Fable dispatch cap to zero (G7). A stale, missing or out-of-schema reading (S28) does not count; then only StopFailure (G6) and the dispatch count (G7) apply. With no active session or low RAM the panel does not read, and the reading ages. The status line still has no per-model field.
- **R6, subagents that escape P1:** in spike S8 of part 2, two paths opened a subagent without going through P1:
  - a skill with `context: fork` typed by the user opens a subagent (SubagentStart) with no PreToolUse for Agent or Skill; it only goes through the UserPromptSubmit of the typed prompt;
  - a `SendMessage` to a subagent that has already finished produces a PreToolUse for SendMessage and a new SubagentStart, which reopens the subagent outside P1; the hook cannot tell the reopening of a finished agent apart.

  `Workflow` (PreToolUse Workflow) and a background Agent go through P1. A Skill invoked by the model (the Skill tool) was not tested. Both escapes stay declared, with no code change: the `Skill` matcher is not added, because it would block every skill (decision 16 of the part 2 plan).
- **A lock lost with `guarda.json`:** deleting `guarda.json` after the condition has passed (for example, the week is back to 50%) loses the recorded G4 lock. The guard derives again from the live condition (spec §4.5), which no longer trips.
- **G7 without a readable reset:** a G7 lock whose official reset cannot be read (`resetsAtMs` null) has no end until `/hadouken:liberar fable`.
- **Plugin agents and `Workflow`:** the frontmatter of a namespaced agent (`plugin:agent`) is not read. Without an `effort` parameter on the Agent call or `CLAUDE_EFFORT`, it profiles as `desconhecido` (unknown) and escapes the Fable and G5 locks (an event records the unknown dispatch); G1 to G4 lock it like any dispatch. `Workflow` always profiles as `desconhecido`.
- **Race between sessions:** two sessions that read, change and write the same file at the same time can lose one record (a Fable dispatch, a limit, a model).
- **Window between `lstat` and `open`:** a file swapped for a link in that interval is not seen as a link.
- **P5:** `..` is collapsed before links are resolved, so a path with a link followed by `..` can reach the data folder without being recognised. A case-insensitive file system on macOS is not handled.
- **Entrypoint:** in spike S12 of part 2, the `claude -p` session opened from the Bash of a VS Code session got `CLAUDE_CODE_ENTRYPOINT=sdk-cli`, and the release hook already refuses it by entrypoint (it refuses every value starting with `sdk`). `claude-vscode` stays accepted, because it is the entrypoint of `/hadouken:liberar` typed in VS Code; refusing it would refuse the user too. If a future version passes `claude-vscode` to the `-p` child, the defence is P4's fixed rule, which always denies the Bash or PowerShell command that calls `claude` with the release request; an obfuscated command escapes it (R1).
- **SessionStart inside a subagent:** the session start that runs inside a subagent (its compact arrives with the parent session's `session_id`) does nothing: it does not register, rewrite the shims, inject a line or record a model. The parent session's model does not change; recording the subagent's would lift P2 and P3 in a Fable session.

**Compatibility rule** (v0.2.0): new data always goes into a new file, never into a new key of a file that an earlier version validates strictly. v0.1.0 treats an `alertas.json` with an extra key as invalid and rewrites it; with mixed versions (a session opened before the update keeps the previous version's hooks), the two would repeat notices to each other. That is why the projection memory lives in `projecao.json`, which v0.1.0 does not know, and `alertas.json` keeps the exact v0.1.0 format.

**Honest limit:** a malicious skill or program that already runs code as the same OS user can change any file of that user, including `settings.json` and the plugin itself. No plugin can prevent that. This plugin guarantees that it does not widen that power, and that it undoes tampering with its shims on every session.

## What the plugin never does

- **Network:** with learning off, the plugin opens no connection of its own. Its only network access is read-only `gh api`: the command is always `gh api <endpoint>`, without `-f`, `-F`, `--input` or `--method`, so it is always a GET. It is run by the `/hadouken:consumo` report, for the repos listed in `~/.claude/hadouken/config.json`. If no repo is configured there, it uses the repo of the `origin` remote of the current folder, read locally with `git remote get-url origin`, which does not touch the network. At most 3 repos per call, with a 15-minute cache. Since v0.3.0, the VS Code panel runs `claude -p /usage` (S26): Claude Code itself talks to Anthropic, through its own official command and your session. The plugin reads no credential, calls no endpoint and spends no tokens: `/usage` is a local command, with no model call. Since v0.4.0, with learning on (optional, off by default), there are two more: the one-time Collector download (L7) and the OTLP that Claude Code sends to the Collector on `127.0.0.1`, which never leaves the machine (L4).
- **Telemetry:** none. Nothing is sent to any service, including the plugin's author. Local learning receives Claude Code's OpenTelemetry only on `127.0.0.1` and keeps it, filtered, in the data folder (L3); nothing goes to any service.
- **Tokens and credentials:** the plugin never reads, logs or stores an access token or credential. The GitHub login belongs to `gh`, and the process environment is passed to `gh` without the plugin examining variable values. The "tokens" in the report are usage counts read from transcripts. From transcripts, the index keeps only each file's relative path, session and request ids, numbers, dates, model, effort and the project name.
- **Writes outside `~/.claude/hadouken/`:** the plugin writes only inside `~/.claude/hadouken/`, or the folder named by `HADOUKEN_HOME` when that variable is set (see "Environment variables" below). The single exception is `~/.claude/settings.json` (or the file named by `HADOUKEN_SETTINGS`, when set), which changes only when the installer command runs with `--aplicar`, or with `--remover` to undo it, and then only the `statusLine` key changes. The one-command installer also writes `extraKnownMarketplaces["claude-hadouken"]` there and `false` for the old third-party copies in `enabledPlugins` (K1). The documented path for this is `/hadouken:instalar`, which the model cannot trigger and which asks for explicit confirmation before writing. Next to `settings.json`, in the same `~/.claude/` folder, the installer creates a backup (`settings.json.bak-hadouken-<time in ms>`, mode 0600; it keeps the 5 most recent and deletes its older ones) and a temporary file for the atomic swap (`settings.json.hadouken-<hex>.tmp`, removed right away). If `~/.claude/` does not exist, it creates it. The other exception (v0.3.0) is the panel extension, which the VS Code CLI installs into its own extensions folder (S27). Since v0.4.0, learning's `ligar` and `desligar` change only the telemetry keys in the `env` of the same `settings.json`, with the same writer and the same backup (L5).

The plugin reads, without writing: the transcripts in `~/.claude/projects/` (or `$CLAUDE_CONFIG_DIR/projects`), the JSON Claude Code hands to the status line, and hook stdin.

## Environment variables

The Claude Code session environment is trusted. Whoever controls it (a project's `settings.json` `env`, direnv, a devcontainer, the shell that started Claude Code) already controls `PATH` and `NODE_OPTIONS`, and with them any program the session runs; that is out of scope. The variables below apply whenever they are set, not only in the plugin's tests, and as paths they accept only a complete absolute path (on Windows, with a drive letter or UNC):

- `HADOUKEN_HOME`: the data folder, instead of `~/.claude/hadouken/`; everything the plugin writes, the shims in `bin/` included, goes there. Set to any other value (relative, empty, blank; on Windows, also `\folder` or `C:folder`), it leaves the plugin without a data folder: the bar and the hooks write nothing, `/hadouken:consumo` only reads, the installer refuses with reason `pasta-dados-invalida`, and the default folder is never used instead. Before writing, the installer shows the folder and where it came from (`pastaDados` and `origemPastaDados`), and the `/hadouken:instalar` skill warns when it comes from this variable: the bar saved in `settings.json` points to that folder in every project. The same goes for the refusal when `settings.json` is a link: the `manual` key it offers to paste by hand points to that folder.
- `HADOUKEN_SETTINGS`: the `settings.json` the installer edits, instead of `<CLAUDE_CONFIG_DIR>/settings.json` or `~/.claude/settings.json`. Set to any other value, the installer refuses with reason `hadouken-settings-invalido` and never falls back to the default file.
- `HADOUKEN_TESTE_GH`: only the exact value `ausente` has an effect: `/hadouken:consumo` does not call `gh`, and the GitHub section is reported as unavailable. The plugin's tests use it. Any other value is ignored, and no value of it ever becomes a program: `gh` is always the one found on `PATH`, by absolute path.
- `HADOUKEN_SEM_PAINEL`: with the exact value `1`, SessionStart neither installs nor updates the VS Code panel extension (v0.3.0). If the variable is in VS Code's own environment, an already installed extension also stops running `/usage`. To remove the panel for good: `code --uninstall-extension gariolilabs.claude-hadouken-painel` and reload the window.
